# A warm long-running n2f process: design note (v0.9 M7; built as `cli/engine.py`, S-305)

Written 2026-11-07 by the wave 2 overseer. The maintainer asked (Q7, S-300) for this note before the
process is built. Measured basis: S-295 (tier 1 table, one-parameter rebuild, quiet host).

## What it saves, and what it does not
Of a 10.4 to 10.9 s rebuild: interpreter and package imports 1.1 s, CAD kernel import 2.8 s, rules 5.7 s,
rest 0.9 s. A process that already holds the imports and the kernel pays none of the first two: the same
rebuild measured in one process took 5.7 s (3.5 s without renders), so it saves about **4.2 s** (a no-change
build 1.4 s becomes about 0.3 s). The rules themselves (geometry, checks, parts list, manual, report)
are not touched: they rerun for any change that reaches them (11 to 12 of 14 rules even for a one-part
parameter), so the process alone never reaches 1 s. Order of value: faster rules and renders first (this
wave), the warm process on top.

## Shape
- One engine process **per product folder**, started on demand (the first `build`, `check`, `ecr impact`,
  `undo`, `concept switch`, `report` … in that folder starts it in the background) or with
  `n2f engine start`; `n2f engine status` / `stop` complete the verbs. The CLI is the client; the engine
  runs the very same command function in-process, so the command's behaviour is one code path.
- Transport: a Unix domain socket in the per-user runtime folder (see "Flexibility" below; mode 0600, under the owner's
  folder; no network port), one request at a time (a lock; a second command waits, as the test lock does).
  The request carries argv, cwd and the environment variables n2f reads (`N2F_*`); the engine streams stdout and stderr back and returns
  the exit code. Ctrl-C in the client cancels the request (the engine finishes or discards the rule in
  flight and stays up).
- Lifetime: exits after 15 minutes idle, on `engine stop`, when the product folder disappears, or after 200
  builds (the CAD kernel leaks a little per build; a recycle bounds memory). A pid file plus the socket
  are removed on exit; a stale pid file is detected by connecting.

## How it picks up model edits (no watching)
Nothing is watched. **Every request starts like a fresh command:** `load_product` re-reads the
folder (0.1 s warm), the build manifest and file hashes decide what reruns, exactly as today. The
product's own Python (`model/geometry/*.py`, `calcs/*.py`, domain screens) is loaded by file path on
every build, so the engine drops those modules from `sys.modules` before each request. Caches the engine
may keep are keyed by content: parsed YAML and the style by (path, mtime_ns, size), nothing keyed by
name alone.

## Stale-state risks, and the answer to each
| Risk | Answer |
|---|---|
| The package itself changed (upgrade, or a developer edits `src/`) | The engine records the package version and the newest mtime of its loaded files at start; the client compares on every request and restarts the engine on a difference |
| A different interpreter or environment runs the CLI | The socket name carries a hash of the interpreter path and package version |
| Module-level state in the package (registry install state, `lru_cache` tables, console objects, `os.environ`, cwd) leaks between commands | Each request runs in a fresh `Registry` install and restores `os.environ` and cwd afterwards; a test drives two different products and two environments through one engine and compares output with cold runs; any `lru_cache` found keyed on a path is replaced or cleared |
| The engine crashes (kernel fault, out of memory) | Before the command was sent: the client runs it in its own process. After: by the verb's class (see "A dropped connection"): a `SAFE` verb is run again by the client, one that changes state is never repeated and says what to look at and run; the next command starts a new engine |
| A command that must not share state (`init`, `release`, `publish`) | They run in-process in the client; only an allow-list of verbs goes through the engine |
| A hung engine | The client times out connecting (1 s) and falls back to a cold run |
| Output differs from a cold run | The test suite runs a fixed set of commands both ways and compares stdout, stderr and exit code; `N2F_NO_ENGINE=1` turns the engine off, and the test suite keeps it off by default (S-196: tests start from prebuilt copies in the test process already) |

## The CLI and the MCP server
- CLI: transparent. The client starts the engine only for the allow-listed verbs and only when
  `N2F_NO_ENGINE` is unset; it never prints about it, except `n2f engine status`.
- MCP server: today `mcp/tools.py` spawns an `n2f` subprocess for every tool call, so an agent through
  a chat client pays 1.1 s of start-up (and 2.8 s for the kernel on anything that builds) on each call.
  With the engine the MCP tools connect to the product's socket instead of spawning (same request, same
  result text and JSON); when no engine is reachable they spawn as now. The MCP server stays a thin
  generator over the verbs (R14); it gains one client function, not a second code path.

## Cost to build, and what to watch
About 5 hours: the socket server and client (`cli/engine.py`, a new module; no `core/` file if the
registry reset is a function the package already has, else one), the allow-list, the cold/warm
comparison test, the MCP client function, and the guide's one paragraph. The thing to decide before it is
built: whether the 200-build recycle and the 15-minute idle limit are right (both are guesses).

## Wire format and paths (decided by the maintainer, built in M7-engine)
- **Wire.** Newline-delimited JSON over the Unix socket, one object per line, UTF-8; every object has
  `"v": 1` and `"t"` (type). The client sends `hello` (`pkg` the version, `code` a hash of the newest
  mtime of the package files, computed by the same function in both, `py` the interpreter); the engine
  answers `ready` or `refuse` (`why`: version, package files changed, interpreter, protocol). On a
  refusal, EOF, a timeout (1 s to connect, 1 s for the hello) or any failure **before `ready`** the
  client runs the command cold in its own process; after a package mismatch it also asks the old engine
  to exit (`stop`), and the next command starts a new one. Then `run`: `argv`, `cwd`, `env` (only
  `N2F_*`, `GIT_*` and the named few the CLI reads: colour, width, `PATH`, `HOME`, locale, cache dirs),
  `tty`, `cols`; two additions: `etty` (stderr is a terminal, since `>file` can split the two) and
  `prog` (the program name click prints in usage errors, so a usage error reads the same). The engine
  streams `out` and `err` chunks (`d` is the text) in order through one writer lock, and ends with
  exactly one `exit` (`code`). An internal failure is `error` (`msg`) then `exit` 70. Also accepted
  without a hello: `stop` (answered `bye`) and `status`.
- **A dropped connection after `run` (decided by the maintainer: design every outcome for the agent
  first: a stated outcome, machine-readable under `--json`, the exact next step).** Every forwarded
  verb has a class in the one table `VERB_CLASSES` in `cli/engine.py` (a verb in neither it nor
  `NEVER_FORWARD` fails `tests/unit/test_engine_classes.py`, so a new verb must choose).
  `SAFE` (it reads, or the rules re-run only what is stale; build, check, status, impact, graph,
  validate, lint, checkpoints, context, docs, `ecr impact|list|show`, `concept list|show|build|board|lint|compare`):
  the client prints one stderr line ("the n2f engine stopped during this command; running it again
  without the engine") and runs the command cold itself. To keep an agent's output free of
  duplicates, when stdout is not a terminal the client holds the engine's `out`/`err` chunks until
  `exit` and writes them then, so a rerun never repeats partial output; on a terminal it streams
  live and a rerun repeats output after the one line. `changes_state` (undo, redo, rollback,
  `ecr start|quick|approve|close|abort`, `concept new|promote|reject|switch|fork-from-model`):
  never repeated. Exit 70 and a stderr text with what happened ("stopped during `n2f undo`; the
  change may or may not have been made"), the read-only verb that shows whether it did (`look_at`,
  the table's, with the original `--dir`: `n2f checkpoints` for undo, redo, rollback, concept
  switch; `n2f ecr list` for the ecr writers; `n2f concept list` for the other concept writers)
  and the exact command to run if not ("run again: n2f <the original argv>"). When the argv has
  `--json`, stdout is one object `{"error": "engine_stopped", "changes_state": true,
  "outcome": "unknown", "look_at": ..., "rerun": ..., "exit": 70}` and the text stays on stderr.
  The MCP path (`capture`) follows the same rule: a `SAFE` drop returns "not served" so the MCP
  server spawns the CLI; a state-changing drop returns exit 70 with that outcome. Failures before
  `ready` (refuse, mismatch, silence) are unchanged: run cold, no message.
- **Socket path (replaced, see "Flexibility").** First rule was `<product>/build/.n2f/engine.sock`
  when short, else a hashed `/tmp` path.
- **Built beyond the note.** The engine is started by the first allow-listed command (before it
  when none runs, so that command stays cold; the rule "only where `build/` exists" was replaced, see
  "Flexibility") or `n2f engine start`; the
  allow-list is build, check, status, impact, graph, validate, lint, undo, redo, rollback, checkpoints,
  every `ecr` and `concept` verb, context and docs. `cli/entry.py` is the new light entry point (the
  `n2f` script now points there): the decision is made before `cli/app.py` imports every command, so
  the client pays only the interpreter. A request runs on the engine's main thread; hello, status and
  stop are answered at once, so a second command waits for its turn instead of timing out. The 15
  minute idle limit and the 200 request recycle can be set for tests with `N2F_ENGINE_IDLE` and
  `N2F_ENGINE_MAX_REQUESTS` in the engine's start-up environment. The kernel announcement ("loading the
  CAD kernel…") does not appear warm: the kernel is already loaded.

## Flexibility (maintainer, S-313: the engine works in any initialised product folder; agent first)
- **A. One path rule.** Engine files (socket 0600, `engine.pid`, `engine.lock`, `engine.log`) always
  live in `/tmp/n2f-<uid>/<first 16 hex of sha256(realpath of the product)>/` (both folders 0700,
  owned by the user, never a symbolic link; refused otherwise). No path-length special case, nothing
  under the product, so the engine never creates `build/` and never puts runtime state in it.
  Reason (corrected, S-314): `build/` is generated output, and a socket, a lock and a pid file are
  runtime state, not output (`ecr impact` copies `build/`; it needed a socket exception). It is not
  about `n2f status`, which does not read whether `build/` exists (its gate reads the manifest's
  part and assembly entries); a test shows `status` identical with no `build/` and an empty one. The log is what the engine process printed (a crash shows there); the folder stays after an
  engine exits (lock and log), tests remove it. The `ecr impact` copy of `build/` needs no socket
  exception any more.
- **B. Any initialised product.** "Initialised" is a folder with `n2f.yaml` at or above the cwd or
  `--dir`. Any classed verb there may start the engine after a cold run, built or not; `spawn` does
  not need `build/` and `n2f engine start` does not create it. `n2f init` starts the engine when it
  is enabled (the kernel warm-up of `cli/kernel.py` stays only for `N2F_NO_ENGINE=1`, and
  `N2F_NO_WARMUP` does not apply to the engine). The engine preloads the package and the kernel
  before it listens, so a build that arrives while it loads simply runs cold.
- **Status.** `n2f engine status` says, when none runs, whether the next command will start one (an
  initialised folder with `N2F_NO_ENGINE` unset, or why not: set, or an engine still loading) and
  the command that starts it now. `--json`: `running`, `will_start_on_next_command`, `reason`,
  `start_command`, `socket`, `pid`, `idle_s`, `idle_left_s`, `requests`, `busy`, `version`.
  `n2f engine start` refuses (`engine_disabled`) while `N2F_NO_ENGINE` is set, since commands would
  not use the engine.
- **Errors under `--json`.** One object on stdout, `{"error": "<code>", "message": "<plain words>",
  "next": "<exact step>"}`, same exit code. `N2FError` carries `next=`/`code=` (and class defaults:
  not-a-product points to `n2f init`, a model error to `n2f validate`, a build error to `n2f build`,
  a gate to `n2f status`, a change request to `n2f ecr list`; the generic fallback is "run `n2f
  --help`"); a failed check prints its own result, no second object. Usage errors (exit 2) are caught
  in `run_app` (`cli/app.py`), the one entry both the CLI and the engine call, so a command reads the
  same warm and cold. The dropped state-changing run (70) has the same three fields plus its own.
  Real exit codes: 0 ok, 1 error, 2 failed check or usage error, 3 gate refused, 4 environment, 70
  engine stopped under a state-changing command.
