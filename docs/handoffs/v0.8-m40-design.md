## What a change row is
The oracle file gains an optional `changes:` list. Each row is one planned change request of the
spec's section 6, judged on **the product as the change leaves it**, by the same finders the
top-level `figures:` and `facts:` use. No row names an id (the oracle's rule: outcomes, never ids).

```yaml
changes:
  - name: ecr-1                      # a label for the report, never looked up
    what: "ECR-1: top 30 to 31 mm, legs 699 mm"
    kind: parametric                 # parametric | design: the request's kind
    words: "top.*31|31 mm"           # regex (case-insensitive) over a request's title and reason:
                                     #   how an agent's own request is found (below)
    sets:                            # the replay of a parametric change: parameters found by
      - {value: 30, unit: mm, words: "top", to: "31 mm"}   # value (in that unit's dimension)
      - {value: 700, unit: mm, words: "leg", to: "699 mm"} # and a regex over name/description
    edits:                           # the replay of a design change, applied in order; each fails
      - {file: model/parts/top.yaml, find: "...", replace: "..."}   # loudly when `find` is absent
      - {file: model/parts/hinge.yaml, remove: true}
      - {file: model/parts/channel.yaml, content: "..."}
    outcome: accepted                # accepted: no requirement fails; refused: at least one does
    fails: ["tip"]                   # refused only: each regex matches exactly one failing
                                     #   requirement (title or message); no other one fails
    figures: [ ... ]                 # Figure rows, exactly as at the top level
    facts: [ ... ]                   # Fact rows, plus the new `signoffs_lost` (below)
```

Schema rules (pydantic, unknown fields are errors, as the rest of `oracle_schema.py`):
- `sets` and `edits` may both be present; at least one of `sets`, `edits` is required.
- `fails` only with `outcome: refused`, and required there (a refusal says what refuses it).
- A `sets` row's `value` is matched against `model/parameters.yaml` values converted to `unit`
  (`convert` in `oracle_match.py`), relative tolerance 1e-6; `words` narrows several candidates.
  None or several left: the row is a FAIL naming what it found (as every matcher does).
- New fact `signoffs_lost`: the number of sign-offs the change invalidates or removes, read from
  the request's impact (`signoffs_invalidated` plus `signoffs_removed` in `n2f ecr impact --json`).
  Numeric, judged like the other numeric facts. Allowed only inside a change row.
- New figure finder `impact: <dotted path>` into the same impact JSON (`mass.after`,
  `cost.delta`), allowed only inside a change row.

## How a row is judged
Everything happens in a scratch copy, never in the folder given: `shutil.copytree` of the product
with its history (`.git`) and its `build/` (so a prebuilt copy stays prebuilt), into a
`tempfile.TemporaryDirectory`. One copy per change row; rows do not see each other.

1. **Which request.** Read `changes/*.yaml` of the product. A request whose `kind` equals the row's
   and whose title or reason matches `words` is the agent's own. Exactly one: judge it (2a).
   None: replay (2b). Several: FAIL "N change requests match".
   With `--replay` (and `evaluate(..., replay=True)`), always replay. The CI test replays.
2a. **An agent's request.** Put the copy at the state the request left: `draft` or `approved`:
   the working folder as it is. `closed`: the checkpoint labelled `Closed <id>: …`; `aborted`:
   the snapshot just before the one labelled `Aborted <id>: …` (the abort saves the work first,
   `ecr/live.py` `abort`). Find them in `n2f checkpoints --json`; restore with
   `n2f rollback <checkpoint id>` inside the copy. Then `n2f ecr impact <id> --json` where the
   request is still open; for a closed or aborted one, `impact` is the stored `impact:` block of
   `changes/<id>.yaml` when present, else the impact finders and `signoffs_lost` FAIL with
   "the request kept no impact".
2b. **Replay.** In the copy: `n2f ecr start --title "<what>" --kind <kind> --set
   param://<found id>=<to> … --json`, then apply `edits`, then `n2f ecr impact --json`. An `edits`
   row that cannot apply makes every assertion of that change one FAIL row: "not replayable on
   this product: <file> has no '<find…>'". A product with no history: one FAIL row naming
   `n2f init .`. A failing n2f command: a FAIL row with its last stderr line (not exit 2: the other
   rows still count).
3. **Judge.** A fresh `Evidence(copy)` (it builds and checks as for the top-level rows). Outcome:
   the requirement results of `n2f check --json` (`requirement_rows` in `oracle_match.py` reads
   them). `accepted`: none fails. `refused`: every `fails` regex matches exactly one failing
   requirement and no failing requirement is left unmatched. Then the row's figures and facts.
   Report rows carry group `change` and `what` prefixed with the change's `name`
   (`ecr-1: sag under the 500 N point load`).

`evaluate()` keeps its signature plus `replay: bool = False`; change rows come after facts.
`render()` and `--json` need no other change. The pending list loses the entries this replaces.

## The two products (section 6 of each SPEC.md; numbers are the spec's, never tuned)
- **table ECR-1** (parametric): top thickness 30 → 31 mm, leg length 700 → 699 mm. Accepted;
  sag 1.66 mm, mass 48.2 kg, cost inside 648–1035 USD (range on the BOM total), tip-over 4.17.
  Reuse the finders of the oracle's existing sag, mass, cost and tip-over rows.
- **table ECR-2** (design): a 500 mm seating overhang at one end (top 2100 × 800 × 30, one end
  575 mm beyond the end glides). Refused by the tip-over requirement; tip-over 1.09.
- **test-stand CR-1** (parametric): rated load 2000 → 2500 N. Refused by the load-cell requirement
  (cell ≥ rated load); deflection 0.131 mm, beam fatigue 7.28, bolt 5.94, buckling 21.8. The swap
  to a 3 kN cell that follows stays a pending entry.
- **test-stand CR-2** (design): the hinged door becomes a vertically sliding door. Accepted;
  mass 16.51 kg, cost inside 446–1635 USD, tip-over 2.03, `signoffs_lost: 2`.
A design change whose edits on the shipped example would exceed about 40 changed lines stays a
pending entry whose reason says so; do not build a large model edit in the oracle. A figure the
replay finds outside tolerance is **not** fixed by editing the expectation: leave the row failing,
mark the test `xfail(strict=True)` with the found and expected values in the reason, and report it
(it is a product or spec finding for the overseer).
