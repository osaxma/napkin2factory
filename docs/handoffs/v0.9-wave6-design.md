# v0.9 wave 6: an agent tries n2f on its own (design, S-327)

Wave 6 pulls the part of Track D (`docs/roadmap/TRACK_D_AGENT_UBIQUITY.md`) a cold agent needs
into v0.9, before M6's gates. Done means: an agent client that can run a local MCP server,
started in an empty folder with a plain request that never names the tool, can make and change a
product through the seven tools below. The rule behind every line here is S-308 (the agent is
the first caller): each tool states its outcome, is JSON, and names the exact next call.

## 1. The seven tools (M8)

Names from Track D §3.2. Schemas are **not frozen** until v1.0: the server's instructions say
"experimental" once, no tool repeats it. The one-tool-per-verb generator goes; `build_argv`'s
argument checks (unknown key, type, path inside the folder) stay as helpers.

Every result is one JSON object as text (`isError` when `ok` is false):
```
{"tool": "n2f_sync", "ok": true|false,
 "steps": [{"command": "n2f build --json", "exit": 0, "engine": "warm"|"cold",
            "seconds": 4.8, "result": <the verb's --json object> | "error": <its error object>}],
 ...the tool's own summary fields...,
 "next": {"tool": "n2f_...", "arguments": {...}} | {"say": "<what to do, plain>"}}
```
`next` is never "run n2f --help". A verb's own `next` (a CLI command) is mapped to a tool call
when one of the seven covers it (a table in `mcp/`, tested against the real command tree),
otherwise passed as `{"say": ...}`. A tool's steps run in order under the runner's lock; a step
that fails stops the sequence unless the table below says otherwise, and the result names it.

| tool | arguments | steps | summary fields |
|---|---|---|---|
| `n2f_init_product` | `name`*, `region`*, `units`*, `template` (blank), `style` | `init <folder> --json` on the opened folder itself | files made; `read_first`: the folder's `AGENTS.md`, `roles/pm.md`. Refuses a folder that already has `n2f.yaml` (`next`: `n2f_sync`). Then starts the engine. |
| `n2f_napkin_sync` | `concept` (one card; default all), `render` (true) | `concept lint`, `concept build [--all]`, `concept board` | each card: id, title, screened pass/fail, the reasons; lint findings; the board's path. A lint failure stops before the build. |
| `n2f_promote_or_switch` | `action`* (`new`, `promote`, `switch`, `fork`, `reject`, `compare`), then the verb's own arguments | the one `concept` verb (`fork` = `fork-from-model`) | the verb's result; for `promote` and `switch`, `next` is `n2f_sync`. |
| `n2f_context` | exactly one of `uri`, `topic` | `context <uri>` or `docs <topic>`; neither: `docs` (the list) | the slice or the page. A uri the verb does not take gets `next` naming the kinds it does (do not widen `n2f context` this wave). |
| `n2f_sync` | `target`, `part`, `render` (true) | `validate`, `lint`, `build`, `check`, `status` | gates, failing checks (id and message), open choices, the report's path, per-step seconds. A failing `check` (exit 5) is an outcome, not a stop: `status` still runs. |
| `n2f_decide` | `check`*, `pick`*, `by`*, `note` | `decide`, `status` | the decision and the gates after it; `next`: make the change, then `n2f_sync`. |
| `n2f_ecr` | `action`* (`quick`, `start`, `impact`, `approve`, `close`, `abort`, `list`, `show`, `undo`, `redo`, `rollback`, `checkpoints`), then the verb's own arguments (`set` is a list of `uri=value`) | for a state-changing action: `status`, the verb, `status`; else the verb alone | for a state-changing action, `before`, `after` and `delta` of the vitals `status --json` has (mass, cost, check counts: whatever is there, nothing invented). |

`*` required. Arguments are named as the verb's options are (`--by` is `by`); `dir` is in no
schema. The agent writes the model's files with its own file tools: no tool writes a file the
verb would not, and no tool runs a shell command (Track D §3.4).

**Instructions** (the server's, under 1,500 characters, no client or model names): what the
tool is; the loop in order (`n2f_init_product` → read `AGENTS.md` and `roles/pm.md` →
`n2f_promote_or_switch new` and `n2f_napkin_sync` → `promote` → edit files, `n2f_sync` →
changes through `n2f_ecr`); `n2f_context topic=agent-guide` for the rules on talking to the
person; results are JSON with a `next`; a cold first build can take a minute, so a client's
per-call timeout should be 10 minutes; experimental, changes before 1.0.

## 2. Through the warm engine (amends Track D §3.3)

The MCP server does not hold the CAD kernel. It stays a light process and sends each step to
the folder's warm engine (S-305: one per product folder, its socket in `/tmp/n2f-<uid>/<hash>/`,
shared with the CLI), exactly as `ToolRunner._run` does today (`engine.capture`, else a cold
process). Reasons: the engine came after Track D was written; it already solves stale code,
stale state and the dropped connection (S-310); a second warm process per folder would double
memory and split the rules.

- At start, when the folder has `n2f.yaml` and no engine answers, the server calls
  `engine.spawn(folder)`, so the first call is likely warm; likewise after `n2f_init_product`.
- Each step reports `engine: warm|cold`.
- On exit (stdin closed), if no engine answered when the server started and one answers now,
  the server calls `engine.request_stop(folder)`: an agent session leaves no process behind
  (S-291). An engine someone else started is left alone.
- A state-changing step that comes back with exit 70 (`error: engine_stopped`) stops the tool;
  `next` maps its `look_at` to the tool call (`n2f checkpoints` → `n2f_ecr action=checkpoints`).
- `N2F_NO_ENGINE=1` still turns it all off (the tests).
- No progress notifications this wave; the instructions ask for the long client timeout.

## 3. Tests (M8)

Unit tests of the sequencing with a fake step runner (no process); the argument checks; the
`next` mapping against the real command tree; the instructions' length and generic words. One
e2e test, `tests/e2e/test_mcp_flow.py`: a prebuilt copy of `examples/table`
(`copy_product(..., prebuilt=True)`), driven only through `ToolRunner.call` (or the protocol
over stdio once): `n2f_sync`, `n2f_ecr quick` on one parameter, `n2f_ecr undo`, checking the
vitals' delta and its reversal. One test that `n2f_init_product` in an empty folder makes a
product. Keep it in `check-fast` only if it is under 30 s; else mark it as the other e2e tests.

## 5. Errors an agent can act on (M9)

- **B-0309:** an exception outside the command in the engine (`run_in_process`'s
  `except Exception`, and any path that prints `error` then exits 70) prints under `--json` one
  object on stdout, `{"error": "engine_internal", "message": <last line>, "next": <exact
  command>, "log": <the engine log path>}`, the traceback only to the log and stderr; without
  `--json` plain stderr as now. For a safe verb, `next` is the same command with
  `N2F_NO_ENGINE=1`; for a state-changing verb, the verb's `look_at` first.
- **B-0310:** give each common raise site its exact `next=`: an unknown id (part, assembly,
  requirement, concept card, change request, check, checkpoint) names the listing command
  (`n2f status`, `n2f concept list`, `n2f ecr list`, `n2f checkpoints`) with the folder's
  `--dir` when one was given; a missing file names the file and the command that writes it; a
  bad value names the allowed ones. A test walks the sites it changed. Report how many of the
  68 `raise N2FError`/`ModelError` sites now carry one.

## 6. A cold agent's setup (M10)

- **`n2f doctor --fix`:** fixes what it can without touching the system or any client's
  settings: Playwright present without its browser → `python -m playwright install chromium`;
  every other row that is not ok gets an exact `next` (the mcp extra: `uv tool install
  "napkin2factory[mcp]"` or `pip install "napkin2factory[mcp]"`). A row `MCP server` (ready, or
  needs the extra). Under `--json` each row adds `fixed` and `next`. Exit 0 when nothing fails
  after the fixes, 1 otherwise; without `--fix` nothing changes.
- **The skill** (`SKILL.md`): a section "With the MCP server": the seven tools in loop order,
  one line each; how a client starts it (`n2f mcp --dir <folder>`, or with no install
  `uvx --from "napkin2factory[mcp]" n2f mcp --dir <folder>`); the 10-minute call timeout.
- **The guide:** the "Adapting to your client" row for the MCP server names the seven tools and
  the setup line; one short subsection (at most 250 words) after it. The guide's size is a
  measure (9,057 tokens at v0.8): report it. README untouched.

Not in this wave: registry listings, the public page, `n2f skill install`, frozen schemas,
progress notifications, the trust prompt for someone else's folder (Track D §3.4's first two
points).
