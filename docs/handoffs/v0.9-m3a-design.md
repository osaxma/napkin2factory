# v0.9 M3a, the workbench page: the overseer's design (2026-11-08)

The plan is `docs/stages/v0.9-progressive-workbench.md` V1 to V8 and §5 M3a; Track C §2 and §3.3
are the brief it amends. This file is what the overseer decided on top of them, so that M3a's
tasks, and M3b, M3c and M4 after them, read one design. The decision entry written when M3a
lands summarises it; this file is not a journal. Mock screenshots (`docs/reviews/v0.9-m3a-mock-desktop.png`, `-phone.png`): desktop 1440 px and phone
390 px of the table (tier 1), sent to the maintainer before anything was briefed.

- **Top bar.** Name, `revision_label`, the state badge (`stage_label`, in words). Vitals from
  `inspector_index["manifest://product"].vitals`, each value with its label (N5): mass, priced
  cost, envelope, open choices (a link to `#waiting` when there are any). One counts line from
  the checks summary, every status in words, `later` included (B-0134); each count links to
  `#requirements`. The lens tabs are `role="tablist"` buttons. The old side index goes.
- **Lenses.** Five `<div class="lens" id="lens-<name>" data-lens="<name>" role="tabpanel">`,
  one per `core.registry.LENSES` entry, in that order, labelled Workbench, Drawings, Build,
  Checks, History. Each holds the shown sections whose registration names it, in registry
  order, with their markup unchanged except the overview's and the model's. A lens with no
  shown section gets neither a tab nor a panel (V7; no second rule). Only the active panel is
  visible (`hidden` on the others).
- **Where today's sections go** (from the registrations): Workbench: overview (as the
  inspector's product view), model (the 3D pane), interfaces, joints. Drawings: drawings and
  the electrical domain's wiring. Build: parts, build. Checks: safety, requirements, rules,
  sign-offs, manuals, and a new "Check views" section. History: parameters, decisions, change
  requests, and a new "Design directions" section.

## The workbench lens
- Three panes in a grid, `height: calc(100vh - top bar)`, each pane scrolling on its own; the
  lens's other sections follow below as cards (so `#interfaces` and `#joints` still land).
- **Tree** (`role="tree"`, items `role="treeitem"`, `aria-selected`): "Product"
  (`manifest://product`), then each top unit (`unit_uris`) with its children in BOM order
  (assembly entries gain `children`, below), then "Interfaces (n)", "Documents (n)", then one
  group per other URI scheme found in the index (a domain's objects), headed by the entries'
  `kind` with a count. Requirements and rules are not in the tree: the inspector reaches them.
  Parts used several times show `× n`. The tree is built in `workbench.js` from the index only.
- **3D pane**: today's viewer and its controls, moved into a toolbar over the viewer's top
  edge; the help line becomes a `title` plus one muted line under the toolbar. `#part-card` goes
  (the inspector replaces it).
- **Inspector**: renders the selected entry. The product's view is the overview section's
  server-rendered markup (where it stands, waiting on you, scope, next step; the tiles go, the
  top bar carries them). Every other entry is rendered by `workbench.js` from the index:
  - a heading (`title`), the kind in words and the URI in small mono, the status in words;
  - per known core kind (assembly, part, interface, requirement, rule, doc) a fixed field
    list with labels (mass and cost with `mass_label` / `cost_label`; artifacts as paths in
    mono, not links, since `build/` paths do not resolve from the report);
  - any other kind (a domain's) generically: `x_words` shown in place of `x`; scalars as
    label/value rows (key humanised); a URI that is a key of the index as a link; arrays of
    URIs as link lists; objects as rows; arrays of objects as a small table. The package names
    no domain kind (F9, V5);
  - a link's text is the target entry's `name`, else its `title`, on one line; a field that is
    null, empty or `None` is left out;
  - "Used by": every entry whose fields name this URI, computed once from the index;
  - "Go to": one link per `*anchor` field, labelled by the lens holding that anchor
    ("Drawing, in Drawings").
  - Buttons: Frame, Isolate, Show all (viewer `frame`, `ghost`, `reset`).
  - A URI with no entry: "This build records nothing for <uri>." Never a guessed entry (V4).

## Selection (one bus, `workbench.js`)
- `select(uri)`: `null` means `manifest://product`. It sets `aria-selected` in the tree
  (expanding and scrolling to the item), renders the inspector, and updates the 3D: a part in
  `viewer.nodes()` → `viewer.select(uri)`; any other entry → `viewer.select(null)` and
  `viewer.highlight(<the part:// URIs its fields name, in the scene>)`.
- The viewer's `n2f:select` (a click on a mesh, or empty space with `uri: null`) calls
  `select`; a selection equal to the current one does nothing, so the two never loop.
- Without WebGL (`viewer.settled === 'unavailable'`) the tree and inspector work unchanged and
  the 3D pane says the browser cannot show 3D.
- Links carrying `data-show3d="<uri>"` anywhere in the page open the workbench and select it.

## Deep links and old anchors (V6)
- New form: `#lens=<name>&select=<uri>`, either part optional (`#select=…` alone opens the
  workbench). Written unencoded (`part://top-board`); read with `decodeURIComponent`, so the
  encoded form works too. A selection updates the hash with `history.replaceState`; a lens
  change sets the hash (a history entry, so Back returns to the previous lens).
- An old anchor (`#part-top-board`, `#drawing-apron-frame`, `#requirements`, …): the lens
  holding the element (closest `[data-lens]`) opens, then the element scrolls into view; the
  selection is unchanged. `#overview` opens the workbench with the product selected. An unknown
  anchor opens the workbench. `hashchange` runs the same code as the first load.
- `docs/report-anchors.md` lists every anchor the page promises (section ids, `part-`,
  `drawing-`, `doc-`, `wiring-`, `step-`, `iface-`, `req-`, `choice-` and the like, with the
  lens each lands in) and the new form; a test checks the list against a built table report
  and the test stand's (domain anchors). Ids inside embedded SVGs are not anchors; B-0180
  (M3b) owns the duplicated `wiring`.

## New and changed data (report/ and the mechanical domain's registrations; no core file)
- Assembly entries gain `children`: `[{uri, qty}]`, the direct children in BOM order from
  `rollups.json` `structure` (the tree's only source of hierarchy).
- The product entry's `vitals` gains `envelope` (`{value: "1600 × 800 × 730 mm", raw: [x, y,
  z], label: "computed"}`, from each top unit's `build/assemblies/<id>/props.json` `bbox`,
  combined; left out when no props exist) and `open_choices` (`{value, raw, label: "given"}`
  from `waiting`). The page's counts line gets `later` from the checks summary (B-0134), and
  the requirements filter "only what is not OK" keeps `later` rows visible.
- "Check views" (`id="check-views"`, Checks lens, shown when renders exist): the renders
  moved out of the model section, captioned "Check renders: flat colours tell the parts apart;
  they are for checking the geometry, not the finish." (B-0295).
- "Design directions" (`id="directions"`, History lens, shown when the folder has concept
  cards): each card's id, title, status in words, the parked reason and built figures; a
  relative link to `../concepts/board.html` when that file exists. Card reads must make the
  report stale when a card changes (as the board's rule does); if that cannot be done cleanly
  in the report rule, the section is left out and a row filed, not shipped stale.

## Phone (below 768 px; M3a makes it not scroll sideways, M4 builds the sheets)
- M3a: the top bar wraps (name and badge, then vitals, then counts); the lens tabs become a
  bottom bar; the workbench stacks: 3D at `60vh`, then the inspector, then the tree; wide
  tables get their own scroll box. Nothing scrolls the page sideways at 390 px.
- M4 then: the 3D fills the screen, the tree is a bottom sheet behind a "Parts" button, the
  inspector a sheet that peeks with the selected title and slides up on a pick; keyboard,
  roles and labels (V8).

## Files and hooks for the later milestones
- `report/workbench.js`, inlined by `report/inline.py` after `viewer.js` (V1). Public surface
  `window.n2fWorkbench`: `select(uri)`, `lens(name)`, `current()`, `index` (the parsed
  `#inspector-index`), and the event `n2f:lens` (`detail: {lens}`) on `document`. M3b's
  callouts and M3c's player call `select` / `lens` and `n2fViewer.highlight`; nothing else.
- `report.html.j2` keeps one line at the end of its `<style>`:
  `{% include "print.css.j2" ignore missing %}` for M3c's print stylesheet; in print every lens
  panel is shown (M3c's file overrides `[hidden]`).
- M3b owns `drawings.html.j2` and `wiring.html.j2`; M3a moves them into their lens unchanged.
  M3c owns `build.html.j2` and `builder_plan.py`.
