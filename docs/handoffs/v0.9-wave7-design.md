## 1. Promotion seeds a model that builds (B-0316)

Today `n2f concept promote` writes assembly stubs with `children: []` and a sag requirement
"check it by hand"; the trial's agent then wrote 29 parts and a geometry script by hand for 55
minutes, and the legs came out misplaced. But the card already *is* the model: each massing call
is a kit call with arguments, a material and a placement, and the board drew it right. So
promotion turns the massing into the model, mechanically:

1. **Parts.** One part per group of identical calls (same kit, arguments, material, process
   class, role, rotation and module); `qty` is the group's size. The part id is the names'
   longest common hyphen prefix (`leg-front-left` … `leg-back-right` → `leg`), else the first
   name; a collision gets `-2`. Each part: `kind: custom`, `process` from the call's process
   class, `material: {name}`, `role`, `geometry: {kit, args}` with the call's arguments, a
   `name` in words. No `cost:` (§3 estimates it from the built mass).
2. **The three overall sizes.** The massing's bounding box gives one driving parameter per axis:
   an envelope parameter promotion already seeds whose value equals that axis's extent (a
   three-number envelope entry's `-x`/`-y`/`-z` matches its own axis only; a single number
   matches the one axis it equals, and none when two axes tie), else a new `overall-length`
   (x), `overall-width` (y), `overall-height` (z) with source "measured across the rough shapes
   of C-nnn". Growth rule: x and y grow about the box's centre, z grows upward (the floor stays).
3. **The stretch rule** (per piece, per axis, in the world frame after the call's rotation):
   a piece longer than half the box's extent *spans* it: it keeps its gaps to both faces, so its
   length follows the overall size (an expression parameter `<part>-<arg>`, for example
   `joist-length: {expr: "worktop-x - 70 mm"}`, so the parts list shows the real cut length).
   Any other piece keeps its size and its distance to the face it was drawn nearest (centred
   within 1 mm of the box's centre: stays centred). The bench: changing the length 1600 →
   1800 mm moves the legs from ±700 to ±800 and lengthens the top, joists, rails and shelf by
   200 mm. Which argument is which axis comes from a table each kit declares (block `length/width/
   height` → x/y/z; plate `width/depth/thickness`; tube `length` along its `axis`; frame
   `length/width/height`); a kit without one, or a rotation that is not a multiple of 90°, keeps
   its arguments literal, and promotion's notes say so.
4. **Placement.** One geometry module per seeded assembly, `model/geometry/<asm>.py`, written by
   promotion: a docstring saying in words what it is and the rule above, the driving parameter
   names, a table with one row per placed instance (part, and per axis the face it keeps to and
   the offset in mm, and the rotation), and `build()` calling a package helper
   (`napkin2factory.geometry.seeded`) that reads the driving sizes through `P` and places every
   row. The table is data the agent may edit to move a part; the logic lives in the package.
   Pieces with a `module` go into that module's assembly, in the product's frame; the top
   assembly places its modules at the origin. No interfaces are seeded: the parts meet where the
   card drew them; the notes say joints are the next design step when the owner wants them, and
   a fresh promotion must not fail `n2f check` for their absence.
5. **Structure is checked, never by hand.** A `structure` verify kind (mechanical domain,
   target `asm://<top>#<measure>`, `op`, `value`; measures `deflection`, `yield_factor`,
   `buckling_factor`, `tip_over_factor`) rebuilds the screen's pieces from the built
   assembly's instances and its parts' kits, arguments and materials, takes the loads from the
   parameters promotion seeded from the card's site, and runs the same structural screen
   (`concepts/screens/structural.py`). Promotion writes one requirement per structural row the
   card's screening computed (the sag limit from the card; the factors at the screen's own
   minimums), replacing today's manual sag requirement. A construction the screen does not cover
   gives an unverified result in §2's words, never a pass.
6. **The result names the next call.** Promotion's result (CLI `--json` and `n2f_concept`
   over MCP) lists what it seeded and ends with `next`: `n2f_sync` (CLI: `n2f build`). The
   guide's and skill's promotion lines say: promotion seeds the parts, layout and structure
   checks; build next; never rewrite what it seeded by hand.

Done when: the trial's promoted card (a block-built bench, copied into a test fixture) promotes,
builds and passes `n2f check`; every built instance's box equals its massing piece's box to
0.1 mm; a +200 mm change of the length moves and stretches as in 3; the `structure`
requirements report the same sag as the card's screening; promotion into a folder that already
has parts changes nothing and says so (today's suggestion path).

## 2. The screen covers the everyday bench; otherwise it says so (B-0317)

The trial's promoted card, four 70 mm block legs under side bearers and joists under a two-ply
top, got "two upright columns (a gantry or a portal)": the screen's `_under` needs a leg to
reach the top itself. Extend `structural_top.py`:
- **Load path through bearers.** A leg stands under the top when a chain of pieces stacked
  between them (each touching the next within 1 mm along z, plan overlap) reaches the top.
- **A layered top.** Boards stacked face to face with the same plan (within 1 mm) are one top:
  their `E·I` add (not glued: each layer about its own axis, conservative); a layer's stress is
  its share of the moment, `M·(E·I)_i/Σ(E·I)` over its `Z`. The message says "two layers".
- **Joists and rails that bend with it.** Pieces between the legs and the top running along the
  span (longer than `SPANS` of it) add their `E·I`, as the frame's long rails already do
  (S-206's sharing rule, the table's SPEC §4.1).
Every other shape keeps its row but says plainly, under `structural-deflection`: "not covered:
the structural check models a top on legs, a frame, trestles, or a column with an arm; this card
is <what it found>. Use one of those builds, or keep it and mark the sag for a person to check
(the requirement's `verify: manual`)". The formulas and their citations stay those already in the
screen (Roark, Shigley); no new engineering number.

## 3. Who makes it, and where (B-0319, B-0320)

The bands in `cost_bands.yaml` are shop rates (`woodworking` 9 to 22 USD/kg), so a self-built pine
bench read 886 USD and up against 450. And the region was guessed from a time zone.
- `n2f.yaml` gains an optional `maker: owner | shop` (absent: the old behaviour, shop rates;
  additive, no schema bump, `docs/schema-policy.md` rule 1).
- `cost_bands.yaml` gains a `basis` column, `made` (today's rows) or `materials` (stock bought at
  retail, the owner builds); add `materials` rows for woodworking and welding, US and EU, each
  `verify: true` with its source; no other process class gets one without a source.
- The cost screen judges the budget on the band that matches `maker`; without `maker` it judges
  shop rates as today, and when the materials figure would pass, its message gives that figure
  and the exact next step ("if the owner builds it, set `maker: owner` in n2f.yaml").
- The parts list: a made part with no `cost:` in a product that declares `maker` gets an
  estimate from its built mass, its process class and that band (basis `estimate`, the band and
  date in its note), so it follows a size change. Products without `maker` are unchanged (no
  golden moves).
- `n2f init` (CLI and `n2f_init_product`) takes region and maker; it never guesses either. Given,
  the result repeats them in words ("costs in US dollars, from US prices; the owner builds it")
  with `confirm`: "ask the owner whether this is right before reading costs". Missing, the
  result names each as a question for the owner (`ask`), and costs say "region not set".

## 4. The small rows (B-0318, B-0321, B-0322)
- **B-0318.** `n2f_context` gains a `materials` topic (CLI: the same list from the verb that
  serves the guide's topics): one line per row of `calckit/data/materials.yaml`, its name, the
  words that select it, density, stiffness and strength with units, the process class, and
  `[verify]`. Short enough for a small model (no sources; a `name` argument gives one row whole).
- **B-0321.** A site load given as a mass (`150 kg`) is accepted wherever a force is: it is
  converted at standard gravity (9.80665 m/s², the value `calckit.structural` uses), and the
  screen's given values and the lint result say "150 kg, read as 1471 N (its weight)".
- **B-0322.** Find where the `'float' object has no attribute 'dimensionality'` comes from (a
  bare number reaching a check that expects a quantity; reproduce with a quick change of a
  seeded dimension) and fix it there. A failed `ecr quick` aborts its own request and says so;
  if it cannot, its error names `n2f_ecr action=abort id=<id>` (CLI: `n2f ecr abort <id>`) as
  `next`, never a generic one.

## 5. The trial set-up (overseer, outside the repository)
- n2f installed as a tool from a wheel built from `main` (`uv build`, then
  `uv tool install <wheel>`), so the MCP server runs from that install, not this checkout.
- The client opened on the empty product folder as its workspace, so no picker appears and
  writes inside it need no approval.
- A sandbox (macOS `sandbox-exec` profile, or the client's own settings if they hold) lets the
  agent read and run only inside the trial folder and the tool's install in the `wakeel` home;
  reading the n2f repository is shown to fail before the run.
- The rerun as in wave 6 (a fresh owner persona, Playwright on the client's web page, the same
  model and prompt), its report in `docs/reviews/`, its cost noted.
