### Journal hygiene: why the union-merge duplicates recurred after S-216, and how to stop it
`.gitattributes` sets `merge=union` on `BACKLOG.md` and `DECISIONS.md` (S-097). Union keeps both sides of a hunk that
both sides changed. S-216 handles exactly one outcome: an id present in both Open and Closed (task closes a row
that main edited). I reproduced both outcomes on a scratch repository with the same attribute:
- A: task moves B-2 to Closed, main edits B-2 in Open -> after `git rebase main`, B-2 is in Open (main's text)
  and in Closed. `dedupe_backlog` drops the Open copy. Fixed since S-216.
- B: task edits B-2's text, main edits B-2's text too -> after the rebase, **both versions of B-2 sit in Open**
  (two lines, one id). `dedupe_backlog` leaves them on purpose
  (`tests/unit/test_journals.py:369`, "duplicate inside Open untouched"), so `test_backlog_ids_unique` fails in the
  landing gate, `make land` gives up and the agent repairs it by hand. That is the recurrence.
No duplicate reached `main`: for the 18 commits that touched `BACKLOG.md` since `3253ef3`, none has a repeated id
(checked per commit with `git show <sha>:BACKLOG.md`). So the gate works; the cost is a failed landing.
Stop it: in `scripts/journal_ids.py` extend `dedupe_backlog` to keep the **last** occurrence of an id repeated
within one table (union places the task's line after main's, so the task's wording wins), and flip the test at
`tests/unit/test_journals.py:369`. About 30 minutes, filed below. The same shape can occur on `DECISIONS.md` index
rows; `test_decision_index_matches_entries` catches it, and it has not been seen, so no change there.
