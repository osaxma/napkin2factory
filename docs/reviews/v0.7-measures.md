## 4. Warm incremental rebuild after a one-parameter change

Method: a fresh copy of each example (no `build/`, no `.git`) in a scratch folder; `uv run n2f build` once (cold); once more with nothing changed; then three runs, each after raising the named parameter in `model/parameters.yaml` by 1 mm over the last run, timing `uv run --project <task folder> n2f build` end to end (wall clock, includes `uv run` start-up, geometry, drawings, renders and the report, which is what an agent waits for). The median of three is the measure. The machine was shared with other agents' work; the load was not measured.

| Tier | Example | Parameter raised | Cold build | Nothing changed | Three runs | Median | v1.0 target |
|---|---|---|---|---|---|---|---|
| 1 | `examples/table` | `table-height` 750 mm | 14.9 s | 8.2 s | 14.4 / 14.5 / 14.3 s | 14.4 s | under 1 s |
| 2 | `examples/test-stand` | `column-length` 760 mm | 36.1 s | 8.7 s | 19.4 / 19.5 / 19.3 s | 19.4 s | set from this measurement |
| 3 | `examples/kiln` | `fiber-thickness` 125 mm | 75.0 s | 11.2 s | 55.8 / 50.8 / 50.2 s | 50.8 s | set from this measurement |

Reading it: tier 1 is about 14 times over its target. A build with nothing changed already costs 8 to 11 s, so a floor of fixed work (loading, hashing, checking what is up to date) sits under every number. The parameter chosen for the table (height) reaches nearly every part, so its warm run is close to its cold run; a parameter that reaches one part would run less, and was not measured. Gate A decides whether the target is a floor for any change or for a typical one.

Each product was judged by `uv run python -m tests.benchmarks.oracle <copy> <SPEC.oracle.yaml>` on `main` a88c951 (the oracle files are unchanged since 5011b22, S-236). Rate = passed / (passed + failed); pending rows are things the oracle cannot judge yet and are not counted.

| 1 table | 2 (Gemini Flash) | 47 | 6 | 5 | 89 % | 38 passed, 12 failed |
| 2 test stand | 1 (Claude) | 45 | 0 | 7 | 100 % | 30 passed, 14 failed |
| 2 test stand | 2 (Gemini Flash) | 39 | 6 | 7 | 87 % | 39 passed, 6 failed (judged once) |
| 3 kiln | any | not measured | | | | |
| Shipped examples (the reference) | | table 53 / 0 / 5, test stand 45 / 0 / 7, kiln 47 / 0 / 6 | | | 100 % | |

Client kinds: every trial ran in a terminal agent. IDE agent and desktop chat app over MCP: not measured (Track D). Vendors: two per tier 1 and tier 2.

What the failures are. Table, both vendors: the agents' own massing and sign-off choices and the region they did not set (S-236: the oracle's region row; `n2f init` now asks); the cards of one trial carry screens of their own that name no `deflection` or `tip_over_factor`. Test stand, vendor 2: see `v0.7-spec-trial-stand-2.md` (no electrical model, a fatigue requirement for the beam only, a dropped depth limit, blocks where the spec has tubes). The three older judgements were taken after the package and the oracle had been changed in response to those very trials (S-230, S-233, S-235, S-236), so only the fourth, the Gemini test stand (39 passed, 6 failed, judged once, on the oracle as it stood at 5011b22, which I did not change), was not tuned against; the other three rates are a measure of the package after its fixes, not a prediction for a new agent.

Target (road §2.1): every tier passes with at least two vendors' models and three client kinds. Where it stands: tiers 1 and 2 each ran with two vendors and reach a product with 0 failing checks; none reaches a 100 % oracle rate with both vendors; tier 3 and two client kinds are not measured.
