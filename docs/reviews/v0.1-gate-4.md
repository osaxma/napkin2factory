## 2. Time to first report page

- As a reader with a warm uv cache (this machine): `uv sync` → report on disk = 2.4 + 5.0 + 2.1 + 129.0 + 2.2 ≈ **141 s (2 min 21 s)** of command time; the page then loads in ~6 s. 
- Fresh machine estimate from the cold measurements: 59 s install + 4 s + 2 s + (≈120 s first-load stall + ≈15 s real build) + 2 s ≈ **3 min 20 s**, plus a Python 3.13 download if none is present (not measured), plus ≈ 1.8 GB of disk.
- Within the README's "ten minutes", but ~85 % of the time is the one silent stall in the first `n2f build` (see Blockers).

## 3. Where the README was wrong, missing, or assumed knowledge

1. **Clone URL is dead.** `https://github.com/osaxma/napkin2factory.git` → HTTP 404. The first command of the install block cannot work for anyone who does not already have the folder.
2. **uv installation not covered.** "Requires Python 3.13 and [uv]" links to uv's docs; no install one-liner, no note that `uv sync` will download Python 3.13 itself if missing, and no note that `uv sync` also installs the whole dev tool-chain (pytest, mypy, ruff, twine, playwright, pillow — ≈ 0.9 GB venv). `uv sync --no-dev` is not mentioned. `pyproject.toml` actually allows 3.13–3.14 (`>=3.13,<3.15`).
3. **The first build stalls for ~2 minutes with no output and no warning.** `built part:l-bracket (never built, 121.2s)` at 10 % CPU; reproduced in isolation as `import build123d` taking 119.7 s on first load in a fresh venv (8.7 s afterwards). A reader sees a hung terminal right after `n2f init`. The README should say "the first build takes a couple of minutes while the CAD kernel loads the first time; later builds take ~15 s".
4. **`N2F_OFFLINE` is never mentioned**, yet a plain `n2f build` performs HEAD requests to vendor websites for every COTS part with a `url:` (mcmaster.com got `HTTP 200` during the enclosure build). `examples/kiln/demo.sh` sets `N2F_OFFLINE=1` by default, so the project knows. There is also **no `--offline` flag** on `n2f build` (`n2f build --help` lists only `--target/--part/--clean/--jobs/--no-render/--explain`), although `src/napkin2factory/bom/validation.py`'s docstring claims "`N2F_OFFLINE=1` (or `n2f build --offline`)". The bracket demo itself makes no network call because it has no vendor URL.
5. **`open build/report/index.html` is macOS-only.** Linux readers need `xdg-open`; Windows `start`. The alternative `uv run n2f serve` works (serves `build/report` at `http://127.0.0.1:<port>/`, 200, 1.6 MB).
6. **`uv run n2f …` only works inside the checkout.** The ten-minute block works because `demo` is created inside the repo and uv walks up to `pyproject.toml`. Create the product folder anywhere else and every command fails with `error: Failed to spawn: n2f`. The README does not say this; the installed tool (`uv tool install .`) does not have the limitation.
7. **What "the report" is** is explained only after the block, in one sentence; the vocabulary that the CLI then prints is not: `snapshot`, `Revision`, `stage`, `draft`, `Intake/Design/Verify/Released`, `ECR` (never expanded to "engineering change request"), `impact`, `sign-off`, `COTS`, `Owner view / Engineer view`. All of them are defined in `docs/vocabulary.md`, which the README lists under "Learn more" without saying it is the glossary.
8. **Sign-offs.** The README's only mention is the disclaimer sentence. The bracket template needs none, so the reader never learns what happens when one is required: `n2f check` still exits 0 and prints `needs your sign-off` with the inspection note; `n2f status` prints the exact `n2f signoff REQ-004 --by <name> --statement "…"`; `n2f ecr close`/`n2f release` refuse (release exit 3: `✗ cannot release v0.1.0: the checks are not green yet`). The enclosure template (the other `--template` the README offers via `docs/cli.md`) hits this immediately.
9. **"ships as a diff page" is not demonstrated.** Neither `n2f release v1.0.0` nor a second release produces one (`versions.json` → `"diffs": []`); the reader must know to run `n2f diff v1.0.0 v1.1.0` (only in `docs/ecr-loop.md`). The ten-minute block never mentions `n2f diff`.
10. **`n2f init`'s own "next" hint contradicts the README.** It says `next: open the folder with your AI client and start intake, or run n2f validate`, while the README's next step is `n2f build`. Both work, but a reader does not know whether "intake" is a required step.
11. **Order of the change loop is enforced but not stated.** Skipping `ecr impact` makes `ecr approve` fail with exit 3 (`✗ ECR-002 has no impact report yet; run n2f ecr impact ECR-002 and read it first`). The README comment on the impact line ("what it touches, before anything changes") reads as optional.
12. **`docs/cli.md` lists `n2f doctor`**; the CLI answers `No such command 'doctor'`.
13. **`n2f status` final line** reads `next: released: send the Revision to the manufacturer` — a doubled colon phrase; minor wording.
14. **The product folder lands inside the tool's repo** (`git status` in the checkout shows `?? demo/`). Harmless, but a reader may think they polluted the project. Not mentioned.
15. **Untested README claims**: `pip install -e .` path (not tried), `make check` "≈ 10 min" (not run), the three-doors "planned" items (fine, marked planned).

## 5. Accounts or network beyond package installation

- No account of any kind was needed. No login, token or telemetry prompt appeared.
- Network: package downloads (≈ 905 MB cold); possibly a Python 3.13 download by uv; HEAD requests from `n2f build` to vendor sites (`www.mcmaster.com`) whenever a part has `source.url` and `N2F_OFFLINE` is unset — results cached 7 days in `build/bom/url-cache.json`. The bracket demo made none.
- Playwright: the README never asks for it and does not need to (it says to open the HTML in a browser). I used it only for automated verification. A matching Chromium (1248 for playwright 1.64.1) happened to be cached on this machine, so `uv run playwright install chromium` was **not** needed here; a fresh machine would need that ≈ 150 MB download for the same verification. Note that `uv sync` installs the `playwright` Python package for every end-user because it sits in the default `dev` group.

## 6. Verdict

### BLOCKERS
- **B1. Dead clone URL** (`github.com/osaxma/napkin2factory` → 404). The README's first command fails for the audience it addresses. Fix or replace with "download/unpack this folder" wording until the repository is public.
- **B2. First `n2f build` appears to hang for ~2 minutes with no output** (`part:l-bracket … 121.2s`, 10 % CPU; isolated as a 119.7 s first `import build123d` in a fresh venv, and again as 34.8 s `import OCP.gp` + 64.9 s `import build123d` in a third venv — it is the first load of the 143 MB OCP native library and its siblings, paid once per venv on macOS). On its own a one-off library load is tolerable; silently, right after the README promised a ten-minute run, it reads as "the tool is broken". Either print a "loading CAD kernel (first time only, ~2 min)" line, warm the import in `n2f init`/`uv sync` post-step, or at minimum say so in the README directly under the build line.

### CONCERNS
- C1. Builds go to the network by default (vendor HEAD requests) with no README mention, no CLI `--offline` flag, and a docstring that promises one. Document `N2F_OFFLINE=1` next to `n2f build`, or add the flag.
- C2. `uv run n2f` fails with `Failed to spawn: n2f` from any folder outside the checkout; the README neither states the constraint nor points readers to `uv tool install .` for that reason.
- C3. The README's headline promise "ships as a diff page" is not reachable from the README: `n2f diff` is absent from the ten-minute block and release does not generate one.
- C4. Sign-offs: the reader is not told what `needs your sign-off` means, that `check` still exits 0, or that `close`/`release` will refuse (exit 3) until `n2f signoff` is run. The enclosure template hits this at once.
- C5. `uv sync` installs the dev tool-chain for end-users (≈ 0.9 GB venv, 59 s cold); `--no-dev` is not mentioned.
- C6. `docs/cli.md` documents a non-existent `n2f doctor`.
- C7. `open …` is platform-specific; give `xdg-open`/`n2f serve` equal billing.

### NOTES
- Every command in the two README blocks ran with exit 0 when executed in order, from inside the checkout. Out-of-order commands produce clear, actionable messages (`✗ ECR-002 has no impact report yet; run n2f ecr impact ECR-002 and read it first`; `✗ you have changes that are not saved yet: n2f snapshot saves them …`).
- The report is one self-contained 1.6 MB HTML (no external `src`/`href`, no non-`file://` requests), loads in ~6 s headless, has a working WebGL canvas, and contains everything the README promises: 3D view, drawings, BOM with the "what to tell the manufacturer" column, check matrix, disclaimer. The diff page (`build/site/diff/v1.0.0..v1.1.0/index.html`) has the same properties with two canvases.
- `uv tool install .` works (14.8 s) and the resulting `n2f` runs from any directory; uv's own PATH warning is the only friction.
- `n2f version`/`--help` take ≈ 1.4 s warm and ≈ 5 s on first invocation (bytecode compile); `ecr close` takes 13–15 s because it rebuilds checks — unexplained in output but acceptable.
- Vocabulary (`snapshot`, `Revision`, `stage`, `ECR`, `Owner/Engineer view`) is well defined in `docs/vocabulary.md`; the README should name that file as the glossary rather than "the words we use instead of git's".
- `n2f init` and README disagree on the next step (intake/validate vs build); harmless.
- Timing caveat: the cold-cache run overlapped partly with other builds on the same machine; magnitudes (59 s install, ~120 s first import, ~15 s normal build) are robust, single digits are not.

### VERDICT
**Not ready to hand to a stranger as-is; close once B1 and B2 are addressed.** The tool itself held up: every README command worked in order, the report and diff pages render cleanly from disk, and no account or hidden service is involved. What fails is the onboarding text — a clone URL that 404s, a silent two-minute stall where the README promised a ten-minute run, builds that quietly touch vendor websites, and a headline feature (`diff`) the README never shows how to reach.
