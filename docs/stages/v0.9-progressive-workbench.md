## 0. Why this release
The report holds everything an owner needs, but as one long page: the 3D model is the third
section, below the overview and the safety list, and what the package knows about one part sits
in six or seven sections. A 5-part table gets the same page as the 30-part kiln, wide wiring
diagrams scroll sideways (B-0176), and at phone width the whole page does (B-0232). v0.9 puts the
design at the centre: a 3D workbench where picking a part, in the model or in a tree, opens what
the package knows about it, and five task lenses in place of the scroll. It works on a phone, by
keyboard and in print. It also finishes Track B: the one-version bridges go (R9) and the open rows
of v0.8's definition of done are closed.

## 1. Mission, non-goals, definition of done
**Mission:** picking, isolation and section cuts in the report's viewer; an inspector index built
from the build's own outputs; the workbench layout with five lenses, a pan/zoom drawing viewer, a
build-step player and a print packet; a phone layout, a keyboard path and interaction tests on all
three tiers; the R9 bridges removed and v0.8's open rows closed.

**Non-goals (stay in `BACKLOG.md`):**
- A hosted viewer or any server for the report (D13: one self-contained file).
- Editing the design from the report (the report reads; the CLI and MCP write).
- New geometry outputs for the workbench (STL export, new renders); the lenses show what the build
  already writes.
- Frozen MCP tool schemas, discovery, the v1.0 contract file (Track D).

**Definition of done (the macOS host plus the CI matrix, S-001):**
1. Opening the report on any tier shows the 3D design first, under a top bar with the product's name and version, its state in words, its vitals (mass, priced cost, envelope, open choices; each with its label, N5) and the lenses (V2).
2. A part is picked by clicking its mesh or its row in the assembly tree, and both show the same selection. The inspector shows that node's entry. Double-click frames the part and ghosts the rest. Clicking empty space returns to the product. A section cut works on X, Y or Z with an offset. Orbiting never picks (V3).
3. The report embeds `inspector_index`, keyed by the URIs the package already uses (V4). It is built only from build outputs and recorded reads (D5). Every part, sub-assembly, interface and domain object has an entry, and a test checks every entry against the build it came from.
4. Five lenses replace the scroll page. `#lens=<name>&select=<uri>` deep-links, and every anchor the report has today still lands, in the lens that holds it (V5). On tier 1 a lens with nothing to show is not drawn (V6).
5. The drawings lens fits every SVG to its width with pan, zoom and full screen, and a callout jumps to its part in 3D (B-0176). No anchor appears twice (B-0180).
6. The build lens steps through the plan and highlights each step's parts in 3D. Printing gives the shop packet of Track C §3.4, which a Playwright print-to-PDF test checks.
7. At 390 px no tier scrolls sideways (B-0232), and the tree and inspector are bottom sheets. Every lens works by keyboard. The tree, inspector and tables carry roles and labels, and no status is carried by colour alone. Playwright interaction tests run on `file://`: tier 1 in `make check`, tiers 2 and 3 in `make check-full` (V8, V9).
8. The report stays self-contained, `file://` safe and at most 20 MB on every tier (D13, N10). Sizes and the §11 timings are recorded at each wave.
9. Track B is finished. `ecr new`, `ecr apply` and `ecr reject` are gone, with their MCP tools (V10). The kiln's demos run the live flow (B-0277). v0.8's open DoD rows are closed: B-0269, B-0281 to B-0284, B-0288 to B-0290, B-0292 to B-0294, with B-0275.
10. Gate C (Track C §4) is judged by the maintainer on all three tiers at desktop and phone width. The cold-agent reproduction trial (road §4.3) passes with two vendors. Gates M (engineering and honesty) and N (UX, owner persona) are closed with blockers fixed. The §2.1 measures are recorded, the health review done (S-190), version 0.9.0 set, pins `>=0.9,<0.10`.

## 8. How the overseer runs this plan
As `v0.8-bidirectional-iteration.md` §8, with these differences:
- The coordinator starts one overseer per wave from `docs/handoffs/v0.9-overseer.md`. Each overseer
  leaves the handoff current (Where it stands, In flight, Next, in order) before it stops.
- At most two of the overseer's own subagents at once, until the maintainer raises it. Workers of
  another vendor (`workerctl`) take the well-specified tasks: M5a's test and doc edits, M5d, M2s from
  this plan. Wave 1's tasks have disjoint files: run M2s and M1 first, since wave 2 waits on M2s.
- M3a decides the page's structure, so its overseer writes a short design file in `docs/handoffs/`
  (as v0.8's M3a did) before briefing. M3b and M3c then read the same file.
- Each brief carries V12's rule. After each wave the overseer records the `core/` count and §11's
  timings in the handoff.
- Gate C's screenshots go to the maintainer with one question each (S-078). The cold-agent trial uses
  a different vendor's model from the one that built the workbench.
- Push only when the maintainer asks.
